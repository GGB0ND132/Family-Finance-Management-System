# 家庭收支管理系统后端开发文档

**文档版本：** v1.0  
**依据：** `docs/详细设计.md` v2.0、`docs/系统设计.md`、`需求与架构设计.md`  
**技术基线：** Python 3.11+、FastAPI、Pydantic、SQLAlchemy 2.x、Alembic、MySQL 8、JWT、bcrypt

## 1. 文档目的与当前状态

本文档用于指导后端编码、接口联调、测试和部署，统一各模块的架构、请求/响应格式、异常处理和权限边界。

当前 `backend/` 目录只有依赖配置和 `main.py` 示例入口，尚未实现业务 API、数据模型、迁移和测试。本文档中的“完成”表示详细设计要求；“TODO”表示需要在当前代码库中落地的工作。

## 2. 统一架构

### 2.1 请求链路

```text
客户端
  -> CORS / RequestId / 日志中间件
  -> FastAPI Router（路径、参数、状态码）
  -> Dependency（数据库会话、JWT 用户、家庭/角色权限）
  -> Pydantic Schema（输入和输出校验）
  -> Service（业务规则、事务编排、金额计算）
  -> Repository（SQLAlchemy 查询和持久化）
  -> MySQL 8（InnoDB、utf8mb4）
```

分层约束如下：

- `router` 不直接写 SQL，不实现余额、权限和统计业务；只负责 HTTP 适配。
- `service` 是业务规则唯一入口，所有写操作在 Service 中完成事务编排。
- `repository` 只封装查询和持久化，不自行提交事务。
- `schema` 不复用 ORM Model 作为接口模型，避免数据库字段泄露。
- `core/common` 放置跨模块能力，业务模块之间通过 Service 接口依赖。

### 2.2 推荐目录

```text
backend/
├── app/
│   ├── main.py                 # 创建应用、注册中间件、路由和异常处理器
```

## 3. API 基本约定

- 基础路径：`/api/v1`；健康检查：`GET /api/v1/health`。
- JSON 请求和响应使用 `application/json; charset=utf-8`。
- 受保护接口使用 `Authorization: Bearer <access_token>`。
- 服务端生成 `X-Request-ID`（客户端传入合法值时可复用），响应体中的 `request_id` 与响应头一致。
- 时间使用 ISO 8601，业务精度到分钟，例如 `2026-09-06T13:42:00+08:00`；数据库保存带时区时间。
- 分页默认 `page=1`、`page_size=20`，最大 `page_size=100`。
- GET 的 `family_id`、`scope` 等使用查询参数；POST/PUT/PATCH 放在 JSON 请求体；导入在 multipart 字段中携带 `family_id`；详情和 DELETE 可仅传资源 ID，由后端反查家庭。
- `scope` 只允许 `personal` 或 `family`。个人查询必须由 JWT 用户反查当前家庭成员，不能信任客户端传入的任意 `member_id`。

### 3.1 统一成功响应

除文件下载和 `204` 删除外，JSON 接口均使用：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "01J..."
}
```

列表接口的 `data` 使用统一分页结构：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0
}
```

建议状态码：查询/更新 `200`，创建 `201`，删除 `204`（无响应体）。金额、余额等字段以字符串传输可避免前端浮点误差，例如 `"amount": "12.30"`；若前后端已统一 Decimal JSON 编码，也必须保持两位小数语义。

### 3.2 错误响应

```json
{
  "code": 40001,
  "message": "金额必须大于0",
  "data": null,
  "request_id": "01J..."
}
```

错误 `code` 使用稳定的业务码，HTTP 状态码表达协议层结果：

| HTTP | 业务码示例 | 场景 | 客户端处理 |
|---|---:|---|---|
| 400 | 40001 | 业务参数不合法、金额非正、账户相同 | 展示字段或表单错误 |
| 401 | 40101 | Token 缺失、过期、签名无效 | 清理登录态并跳转登录 |
| 403 | 40301 | 非家庭成员、角色不足、越权访问 | 展示无权限提示 |
| 404 | 40401 | 资源不存在或不属于当前可见家庭 | 展示资源不存在 |
| 409 | 40901 | 用户名/分类重复、余额非零销户、最后管理员保护、并发冲突 | 提示用户刷新或处理冲突 |
| 422 | 42201 | Pydantic 请求结构、类型、必填字段错误 | 按 `field` 定位输入 |
| 500 | 50000 | 未预期异常 | 仅返回通用提示，服务端记录堆栈 |

422 也必须转换为上述统一结构，`data` 可包含：`{"fields": [{"field":"amount","reason":"必须大于0"}]}`。生产环境不得返回 SQL、堆栈、Token 或密码。

### 3.3 响应封装示例

```python
from typing import Generic, TypeVar
from pydantic import BaseModel

T = TypeVar("T")

class ApiResponse(BaseModel, Generic[T]):
    code: int = 0
    message: str = "success"
    data: T | None = None
    request_id: str | None = None

def ok(data, request_id: str, message: str = "success"):
    return ApiResponse(data=data, request_id=request_id, message=message)
```

Router 通过 `response_model=ApiResponse[SomeSchema]` 声明契约；异常处理器统一构造 `ApiResponse(data=None, ...)`。文件导出不套 JSON 外壳，直接返回 `StreamingResponse`，但仍设置 `X-Request-ID`；错误下载响应仍返回统一错误 JSON。

## 4. 异常处理与事务规范

### 4.1 异常类型

在 `app/core/exceptions.py` 定义：

```python
class DomainError(Exception):
    status_code = 400
    code = 40001

class AuthenticationError(DomainError): ...
class PermissionDeniedError(DomainError): ...
class ResourceNotFoundError(DomainError): ...
class ConflictError(DomainError): ...
class ValidationError(DomainError): ...
```

路由或 Service 只抛出领域异常；统一异常处理器负责转成 `ApiResponse`。FastAPI 的 `RequestValidationError`、`HTTPException`、`IntegrityError` 和兜底 `Exception` 均需要注册处理器。

### 4.2 处理原则

1. `get_db` 产生一个请求级 Session；成功由 Service 提交，异常自动 rollback，最后关闭 Session。
2. 数据库唯一键冲突转换为 `409`，不把原始数据库错误返回前端。
3. 余额、流水编辑/删除、转账、批量导入必须在同一事务内完成。
4. 事务涉及多个账户时按账户 ID 升序加行锁（`SELECT ... FOR UPDATE`），避免死锁；失败全部回滚。
5. 读接口只返回当前用户有权访问的家庭数据，不能先查资源再在内存中“过滤”越权结果。
6. 日志记录 `request_id、user_id、family_id、route、status、耗时`；密码、Token、原始账单内容不得写日志。

### 4.3 典型异常请求

| 请求场景 | 响应 |
|---|---|
| 未带 Authorization | `401 / 40101` |
| Token 过期或签名错误 | `401 / 40101` |
| family_id 不存在或用户不是成员 | `403 / 40301`（避免泄露家庭是否存在） |
| 普通成员保存家庭预算 | `403 / 40302` |
| 账户已销户仍记账/转账 | `409 / 40903` |
| 销户时账户余额不为 0 | `409 / 40904` |
| 收支类型与分类方向不匹配 | `400 / 40005` |
| 转出和转入账户相同 | `400 / 40006` |
| 试图删除最后一名管理员 | `409 / 40905` |
| 分页参数超范围或日期格式错误 | `422 / 42201` |
| 导入确认时存在非法行 | `400 / 40020` |

## 5. 认证、家庭隔离与权限

- 密码使用 bcrypt 哈希；登录错误统一返回“用户名或密码错误”，不区分用户名不存在或密码错误。
- `get_current_user` 解析 JWT 并加载用户；所有受保护接口都依赖该函数。
- `require_family_member(family_id)` 校验成员关系；`require_family_admin(family_id)` 进一步校验 `role=ADMIN`。
- 账户、分类、流水、转账、预算、导入批次和报表查询都必须带家庭过滤。
- 普通成员：可维护自己相关的账户和流水；流水权限按账户所属人、资金归属人或录入人规则校验；转账双方或录入人可维护本人相关转账。
- 管理员：可维护当前家庭成员、账户、分类、预算、导入和导出，并拥有普通成员全部权限。
- 家庭始终至少保留一名管理员；管理员不能移除自己或降级最后一名管理员。

### 6.2 核心业务规则

- 收入：`current_balance += amount`；支出：`current_balance -= amount`。
- 编辑流水：锁定旧/新账户，撤销旧影响、校验新字段、应用新影响后更新记录。
- 删除流水：锁定账户、反向恢复余额、删除记录。
- 转账只写 `transfers`，不生成收入/支出流水，不计入预算和收支结余。
- 销户账户不可产生新流水或转账，不计入当前资产，但历史明细和历史报表保留。
- 个人报表按 `beneficiary_member_id` 聚合；家庭报表按当前家庭全部 `transactions` 聚合。
- 预算只统计支出；使用率 `<80%` 正常、`80%~100%` 预警、`>100%` 超支；预算为 0 时使用率返回 0。

## 7. 导入、导出与文件安全

导入流程为“上传/映射 -> 预览 -> 确认”。后端校验扩展名、MIME、大小、必要列、日期、金额、方向、家庭和账户。无时间的日期补为当天 `00:00` 并在预览行提示。去重键固定为：`账户 + 分钟级发生时间 + 两位小数金额 + 去首尾空白备注`，同时检查数据库和当前批次。确认时有效行批量写入流水并更新余额，任何一行失败则整体回滚并将批次标记为 `FAILED`。

导出接口：

```text
GET /api/v1/exports/transactions?family_id={id}&scope=personal|family&from=...&to=...&format=csv|xlsx
```

CSV 返回 UTF-8 BOM；XLSX 使用 `BytesIO + openpyxl + StreamingResponse`，设置正确的 `Content-Type` 和 `Content-Disposition`。导出前重新执行家庭和范围权限过滤，不能导出其他家庭数据。

## 10. 三人协作分工

以下以“后端成员 1/2/3”表示三位同学，实际使用时替换为姓名。每个阶段由一人主责、一人协作评审；数据库迁移、接口契约和测试不得由单人私自修改后直接合并。

### 10.1 P1：核心账本能力

| 成员 | 主责任务 | 主要交付物 | 依赖/协作 |
|---|---|---|---|
| 后端成员 1 | 账户、分类及基础数据 | `accounts/categories` Model、Schema、Repository、Service、CRUD 路由；余额为零删除/有关联销户；默认分类初始化；迁移脚本 | 先完成家庭成员权限依赖；为成员 2/3 提供账户、分类查询接口 |
| 后端成员 2 | 收支流水与金额服务 | `transactions` Model、分页筛选 API；`MoneyService`；收入/支出余额应用、编辑撤销重算、删除回滚；成员权限 | 依赖成员 1 的账户/分类；与成员 3 对齐锁顺序和统计字段 |
| 后端成员 3 | 转账、预算和报表 | `transfers` 原子事务；个人/家庭 summary、trend、by-category、by-member；月度预算、复制上月和预警计算 | 依赖成员 1/2 的模型和金额规则；报表 SQL 只读，不修改余额 |

**P1 阶段验收：** 完成“建家庭 -> 建账户/分类 -> 新增收支 -> 转账 -> 查看预算和报表”主流程；余额、家庭隔离、转账回滚和预算口径测试通过。

### 10.2 P2：数据交换与交付质量

| 成员 | 主责任务 | 主要交付物 | 依赖/协作 |
|---|---|---|---|
| 后端成员 1 | 外部账单导入 | CSV/XLSX 解析、字段映射、预览批次/行、去重键、非法行反馈、确认整体回滚；补充 `openpyxl` 依赖 | 复用成员 2 的流水写入和 `MoneyService`；不得绕过家庭/账户校验 |
| 后端成员 2 | 流水导出与接口契约 | CSV UTF-8 BOM、XLSX `StreamingResponse`、筛选和权限拦截；OpenAPI Schema、示例响应、错误码表 | 与前端确认列名、时间和 Decimal 格式；复核成员 1 导入字段命名 |
| 后端成员 3 | 质量、性能与部署 | 并发锁/回滚/家庭隔离测试；10 万条流水分页性能测试；Docker Compose、启动脚本、默认数据、备份说明 | 汇总成员 1/2 的接口并做集成验收；统一 CI 中的 `ruff`、`pytest`、`mypy` |

**P2 阶段验收：** 导入预览和确认可整体回滚，CSV/XLSX 可按范围导出，核心接口文档可联调，测试和部署命令可重复执行。

### 10.3 P3：可选扩展

| 成员 | 主责任务 | 主要交付物 | 依赖/协作 |
|---|---|---|---|
| 后端成员 1 | 定期账单 | `recurring_rules` 模型、周期计算、启停/编辑 API、到期生成待确认流水；确认后才影响余额 | 复用成员 2 的流水 Service；增加重复执行保护 |
| 后端成员 2 | 凭证附件 | `attachments` 模型、上传/查询/删除 API；MIME、大小、文件名、存储路径和访问权限校验 | 关联 transactions；与部署成员确认持久化卷和备份策略 |
| 后端成员 3 | 平台治理增强 | 审计日志、限流、刷新 Token、异步大文件导入（可按时间选做） | 统一接入 Request ID 和日志；评估对现有 API 响应和部署的影响 |

**P3 阶段验收：** 选定的扩展功能有独立迁移、接口、测试和使用说明；不改变个人/家庭统计、销户和转账既有口径。

### 10.4 协作规则与交接清单

1. 每位成员在独立分支开发，提交信息标明阶段和模块，例如 `P1 transactions: add balance service`。
2. 先合并数据库迁移和 Schema，再合并 Service，最后合并 Router；同一张表只允许一份迁移负责人。
3. 交接必须包含：接口路径和示例、请求/响应 Schema、错误码、迁移命令、测试命令、已知限制。
4. 每个阶段结束由非主责成员进行一次代码评审，并运行完整集成测试；失败项登记到 TODO 或缺陷列表。
5. 如果接口字段需要调整，先更新本文档和 OpenAPI，再同步前端，避免前后端各自维护不同契约。

## 11. 建议开发顺序

```text
工程/异常/认证
  -> 家庭成员
    -> 账户/分类
      -> 收支流水
        -> 转账、预算、报表
          -> 导入、导出、性能与部署
```

每完成一个模块，应同步提交：迁移脚本、Schema、Service/Repository、路由、单元测试、API 示例和 TODO 勾选记录；不得只用前端 Mock 代替后端实现。
