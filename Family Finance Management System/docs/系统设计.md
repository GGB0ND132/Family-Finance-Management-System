# 家庭收支管理系统系统设计

**版本：** v2.0  
**对应需求：** `docs/需求分析.md` v2.0  
**技术基线：** React + TypeScript + Vite + Ant Design；Python + FastAPI + SQLAlchemy 2.x + MySQL 8.0

## 1. 设计目标与范围边界

系统采用前后端分离架构，服务于家庭成员的日常记账、账单文件导入、个人资产分析与家庭收支分析。前端负责页面呈现、交互与输入提示；后端负责身份鉴别、权限控制、金额计算、统计口径和数据库事务；MySQL 负责业务数据持久化。

系统是第三方记账应用，不能也不尝试替代支付平台。因此不包含支付、扣款、充值、提现、票据 OCR、凭证附件、定期账单任务，以及微信、支付宝、银行的实时 API 同步。外部账单仅由用户先在原平台导出 CSV 或 Excel 文件后上传导入。

设计遵循以下原则：

- **人员归属明确：** 每个账户必须属于一个家庭成员；每笔收入或支出同时保存资金归属人和录入人。
- **个人与家庭分视角：** 个人资产按账户所属人统计，个人收支按资金归属人统计；家庭报表汇总全部成员数据。
- **转账不重复统计：** 内部转账只改变个人资产和账户余额，不计入家庭或个人收入、支出、结余和预算。
- **后端为准：** 前端不计算最终余额、权限和统计结果，所有业务规则由后端二次校验。
- **余额强一致：** 收支、转账、导入批次的写入及相关余额变更在数据库事务中完成。
- **历史可追溯：** 有历史记录的账户删除时转为销户，保留历史记录而不允许产生新流水。

## 2. 总体架构

```text
┌────────────────────────────────────────────────────────────────┐
│ React + TypeScript + Vite + Ant Design                          │
│ Pages / Feature Components / Zustand / TanStack Query / Axios   │
└───────────────────────────────┬────────────────────────────────┘
                                │ HTTPS + JSON / 文件上传 + JWT
┌───────────────────────────────▼────────────────────────────────┐
│ FastAPI                                                         │
│ Router -> Dependency -> Service -> Repository -> SQLAlchemy     │
│ Pydantic Schema / Exception Handler / OpenAPI                   │
└───────────────────────────────┬────────────────────────────────┘
                                │ PyMySQL
┌───────────────────────────────▼────────────────────────────────┐
│ MySQL 8.0 (InnoDB, utf8mb4, DECIMAL)                            │
└────────────────────────────────────────────────────────────────┘
```

开发环境中，Vite 在 `http://localhost:5173` 提供前端开发服务，FastAPI 提供 RESTful API，并通过 CORS 允许该来源访问。部署时可由 Nginx 托管前端静态文件并将 `/api` 反向代理到 FastAPI。

## 3. 前端架构设计

### 3.1 前端分层

| 目录/模块 | 职责 |
|---|---|
| `router` | 路由定义、登录守卫、家庭上下文缺失时的跳转处理 |
| `api` | Axios 实例、JWT 注入、统一错误处理、接口类型与请求函数 |
| `stores` | Access Token、当前用户、当前家庭等轻量全局状态 |
| `pages` | 页面级布局、数据查询与组合展示 |
| `features` | 记账、转账、账户、预算、导入等业务组件 |
| `components` | 金额文本、筛选栏、确认弹窗、空状态、图表容器等通用组件 |
| `layouts` | 登录布局、主应用布局、首页独立入口和业务页个人/家庭范围导航 |

### 3.2 页面规划

| 路径 | 页面 | 主要内容 |
|---|---|---|
| `/login`、`/register` | 认证页面 | 注册、登录、退出、登录状态恢复 |
| `/personal` | 个人首页 | 当前成员选定日期（默认当天）的收入、支出、转账与账户变动；个人资产和个人统计 |
| `/family-dashboard` | 家庭首页 | 家庭当月收支、结余、总资产、预算进度、成员对比与家庭统计 |
| `/transactions` | 收支流水 | 页面内个人/家庭范围切换、分页列表、新增、编辑、删除收入支出 |
| `/transfers` | 内部转账 | 页面内个人/家庭范围切换、转出账户、转入账户、金额与转账记录查询 |
| `/accounts` | 账户管理 | 页面内个人/家庭范围切换；个人查看本人账户，家庭按所属人展示账户；支持新增、编辑、删除或销户 |
| `/categories` | 分类管理 | 默认分类展示与自定义收入/支出分类管理 |

| `/reports` | 数据报表 | 页面内个人/家庭范围切换；个人收入来源、支出分类、月度趋势、转账/资产变动；家庭收支趋势、分类占比、成员对比和预算执行 |
| `/imports` | 外部账单导入 | 页面内个人/家庭范围选择、CSV/Excel 上传、字段映射、预览、错误反馈、确认导入 |
| `/exports` | 流水导出 | 页面内个人/家庭范围选择、过滤导出范围并选择 CSV 或 Excel 格式 |
| `/family` | 家庭设置 | 家庭切换、邀请码、成员和角色管理 |

### 3.3 状态与请求策略

- `Zustand` 只保存认证信息、当前用户和当前家庭标识；页面业务数据由 `TanStack Query` 管理，避免在全局状态中保存可过期的报表或余额。
- `Axios` 请求拦截器只添加 `Authorization: Bearer <token>`，不添加自定义家庭请求头。GET 查询接口在查询参数中传入 `family_id`；POST/PATCH/PUT 写接口在 JSON 请求体中传入 `family_id`。服务端必须验证该用户是对应家庭成员。
- 创建、编辑、删除流水、转账、销户和确认导入成功后，使账户、流水、个人首页、家庭首页、预算和报表相关查询失效并重新获取。
- Ant Design `Form` 负责必填、格式和交互提示；后端 Pydantic 和 Service 层负责最终校验。

## 4. 后端架构设计

### 4.1 分层职责

```text
HTTP Request
  -> Router：参数解析、响应状态声明、调用业务服务
  -> Dependency：数据库会话、JWT 用户、家庭成员/管理员身份
  -> Service：权限决策、业务校验、余额处理、事务编排
  -> Repository：SQLAlchemy 查询、持久化与统计聚合
  -> MySQL
```

| 层次 | 主要职责 | 禁止事项 |
|---|---|---|
| Router | 解析输入、声明 Schema、返回响应 | 直接修改余额或拼接复杂 SQL |
| Dependency | JWT 解析、当前用户和家庭身份校验 | 处理具体记账规则 |
| Service | 领域校验、事务、余额影响、权限判断 | 依赖 HTTP Request 对象 |
| Repository | 数据读写、锁定查询、报表聚合 | 返回 HTTP 响应、解析 Token |
| Schema | 输入输出结构、字段格式校验 | 访问数据库 |

### 4.2 后端目录建议

```text
backend/
├── app/
│   ├── main.py
│   ├── core/                 # settings、security、exceptions
│   ├── db/                   # engine、session、base
│   ├── common/               # response、pagination、enums
│   └── modules/
│       ├── auth/  users/  families/  accounts/  categories/
│       ├── transactions/  transfers/  budgets/  reports/
│       ├── imports/  exports/
├── alembic/
├── tests/
├── pyproject.toml
└── .env.example
```

每个业务模块包含 `router.py`、`schemas.py`、`models.py`、`service.py` 和 `repository.py`；小型模块可以合并简单 Repository，但不能把路由、鉴权和复杂业务处理混在同一文件。

## 5. 数据库设计

### 5.1 核心表概览

| 表名 | 关键字段 | 说明 |
|---|---|---|
| `users` | `username, password_hash, nickname` | 系统用户 |
| `families` | `name, owner_id, invite_code, invite_expires_at` | 家庭账本 |
| `family_members` | `family_id, user_id, role` | 用户在家庭内的成员身份与角色 |
| `accounts` | `family_id, owner_member_id, name, type, initial_balance, current_balance, closed_at` | 账户及其所属成员；`closed_at` 非空表示已销户 |
| `categories` | `family_id, name, type, icon, color, deleted_at` | 默认或自定义收支分类，保留历史引用 |
| `transactions` | `family_id, account_id, category_id, beneficiary_member_id, recorder_user_id, type, amount, occurred_at, dedup_key` | 收入或支出流水及导入去重键 |
| `transfers` | `family_id, from_account_id, to_account_id, from_member_id, to_member_id, recorder_user_id, amount, occurred_at` | 家庭内部转账 |
| `monthly_budgets` | `family_id, scope, member_id, month, total_amount` | 个人或家庭月度总预算；个人预算不存在时初始化为 0 |
| `category_budgets` | `family_id, scope, member_id, month, category_id, amount` | 个人或家庭月度分类预算 |
| `import_batches` | `family_id, account_id, uploader_user_id, file_name, file_type, status` | 导入文件、处理状态和结果汇总 |
| `import_rows` | `batch_id, row_number, raw_data, normalized_data, dedup_key, validation_status, error_message` | 导入预览、错误行、去重键和确认前数据 |

`accounts.closed_at` 是销户历史状态，不设计“启用/停用”开关。仅当账户没有任何流水和转账关联时才物理删除；否则删除请求更新 `closed_at`，禁止该账户继续用于新增流水和转账，并从当前资产汇总中排除。

### 5.2 主要关系

```text
users 1 --- n family_members n --- 1 families
families 1 --- n accounts        (accounts.owner_member_id -> family_members)
families 1 --- n categories
families 1 --- n transactions    (beneficiary_member_id -> family_members)
families 1 --- n transfers       (from_member_id/to_member_id -> family_members)
families 1 --- n monthly_budgets --- n category_budgets
accounts 1 --- n transactions
accounts 1 --- n transfers       (转出或转入)
categories 1 --- n transactions
import_batches 1 --- n import_rows
```

### 5.3 约束与索引

- 金额字段使用 `DECIMAL(12,2)`，业务层使用 Python `Decimal`，禁止 `FLOAT` 或 `DOUBLE`。
- `family_members` 建立唯一索引 `(family_id, user_id)`；应用层禁止同一家庭同方向的现用分类重名。
- `monthly_budgets` 建立唯一索引 `(family_id, scope, member_id, month)`；`category_budgets` 建立唯一索引 `(family_id, scope, member_id, month, category_id)`。
- `transactions.occurred_at`、`transactions.created_at`、`transfers.occurred_at` 和 `transfers.created_at` 使用带时区的时间戳并统一精确到分钟，页面及导出按 `YYYY-MM-DD HH:mm` 显示。`transactions` 建立 `(family_id, occurred_at)`、`(family_id, beneficiary_member_id, occurred_at)`、`(account_id, occurred_at, amount, dedup_key)`、`category_id` 索引；`transfers` 建立 `(family_id, occurred_at)`、`from_member_id`、`to_member_id` 索引。
- 所有业务表使用 InnoDB、`utf8mb4` 和外键。跨表的“同一家庭”关系由 Service 层复核，避免仅依赖前端传入的 ID。

## 6. RESTful API 设计规范

### 6.1 通用约定

- API 前缀为 `/api/v1`；普通接口使用 UTF-8 JSON，导入使用 `multipart/form-data`，导出使用文件响应。
- 认证头为 `Authorization: Bearer <access_token>`。家庭资源的 `family_id` 约定为：GET 使用查询参数，POST/PATCH/PUT 使用请求体；DELETE 根据资源 ID 查询其家庭归属。后端必须校验成员归属，禁止使用自定义 `X-Family-Id` 请求头。
- 列表分页参数为 `page`、`page_size`，默认分别为 1、20，`page_size` 最大为 100。
- 统一成功响应为 `{ "code": 0, "message": "success", "data": {} }`；统一错误响应为 `{ "code": 40001, "message": "金额必须大于 0", "data": null }`。

### 6.2 资源接口摘要

| 资源 | 路径示例 | 方法 |
|---|---|---|
| 认证与用户 | `/auth/register`、`/auth/login`、`/users/me` | `POST`、`GET`、`PATCH` |
| 家庭与成员 | `/families`、`/families/join`、`/families/{id}/members` | `GET`、`POST`、`PATCH`、`DELETE` |
| 账户 | `/accounts`、`/accounts/{id}` | `GET`、`POST`、`PATCH`、`DELETE` |
| 分类 | `/categories`、`/categories/{id}` | `GET`、`POST`、`PATCH`、`DELETE` |
| 收支流水 | `/transactions`、`/transactions/{id}` | `GET`、`POST`、`PATCH`、`DELETE` |
| 内部转账 | `/transfers`、`/transfers/{id}` | `GET`、`POST`、`DELETE` |
| 预算 | `/budgets/{month}`、`/budgets/{month}/copy-from-previous` | `GET`、`PUT`、`POST` |
| 个人/家庭报表 | `/reports/personal/*`、`/reports/family/*` | `GET` |
| 外部导入 | `/imports/preview`、`/imports/{id}/confirm` | `POST` |
| 导出 | `/exports/transactions` | `GET` |
| 健康检查 | `/health` | `GET` |

## 7. 认证、授权与数据隔离

1. 登录成功后，后端签发包含用户 ID（`sub`）的 JWT。
2. `get_current_user` 验证 JWT 并获取当前用户；`require_family_member` 复核当前用户属于目标家庭；管理员操作额外经过 `require_family_admin`。
3. 普通成员可以查看家庭数据、创建个人收支和转账；编辑或删除收支流水的条件为“账户所属人为自己”“资金归属人为自己”或“录入人为自己”。编辑或删除内部转账的条件为“转出方为自己”“转入方为自己”或“录入人为自己”，因此转账双方均可编辑。管理员可维护当前家庭全部数据。
4. 账户由账户所属人或管理员管理；普通成员只能创建、编辑和销户本人账户，管理员可维护家庭全部账户。分类和家庭预算由管理员维护，个人预算由当前成员维护；家庭成员可导入账单，导出按个人/家庭范围和当前权限执行。所有资源查询均带 `family_id` 条件，禁止通过单独资源 ID 越权访问。个人查询带 `family_id` 选择家庭，但成员 ID 由 JWT 对应用户在后端解析。
5. 导出接口按当前用户权限过滤；导入确认时重新校验上传人和家庭身份，不能只信任预览阶段的结果。

## 8. 关键事务与统计设计

### 8.1 收入与支出

创建收支流水时，前端校验必填、金额、分类方向和分钟级时间格式，服务层锁定目标账户并再次校验账户未销户、分类方向与流水类型一致、资金归属人为当前家庭成员、发生时间有效且金额大于 0，然后写入流水并更新账户余额。编辑时先撤销原流水对原账户的影响，再按新值应用影响；删除时撤销余额影响后删除流水。任一环节异常即回滚。账户删除或销户前必须锁定账户并检查 `current_balance = 0.00`，余额非零时返回可转出提示并拒绝。

### 8.2 家庭内部转账

创建转账时，前端校验金额、分钟级时间、账户选择和账户不能相同；不设置独立方向字段。服务层以固定 ID 顺序锁定两个账户，校验同家庭、账户不同、均未销户、双方成员与账户所属人一致且发生时间有效。随后扣减转出账户、增加转入账户并写入转账记录。转账不写入 `transactions`，因此不会参与个人或家庭收入、支出、结余和预算统计；个人页面通过转账表展示资产增减。

### 8.3 导入批次

预览阶段只解析 CSV/Excel 文件、保存映射后的预览行和校验结果，不写入正式流水。每行生成标准化去重键 `account_id + occurred_at(分钟) + amount(2位) + trim(remark)`，同时与数据库已有流水和当前批次其他行比较；重复行标记为 `DUPLICATE`，默认不导入。确认导入时重新校验每一行的账户、分类、资金归属人和去重结果，在一个事务中批量写入流水、更新账户余额和批次状态；任一行不满足要求时整体回滚，并返回行号和原因。

### 8.4 报表与预算

- 家庭收入、支出和结余仅从 `transactions` 聚合，不包含 `transfers`。
- 个人收入、支出通过 `transactions.beneficiary_member_id` 聚合；个人资产通过该成员未销户账户的余额聚合。
- 家庭总资产为所有未销户账户余额之和；内部转账前后该数值不变。
- 预算已用金额按范围聚合：个人按当前成员资金归属人的当月 `type=EXPENSE` 流水，家庭按当前家庭当月 `type=EXPENSE` 流水；不保存易产生不一致的冗余累计值。个人预算记录不存在时返回总预算 0 和空分类预算集合，前端初始化为 0 并允许添加或快捷创建预算分类项目；移除项目不删除全局分类。

### 8.5 family_id 与个人查询

- 客户端状态层只保存 `currentFamilyId`，不把它写入自定义请求头。
- GET 资源示例：`GET /api/v1/transactions?family_id=12&scope=personal`；家庭查询使用 `scope=family`，个人查询使用 `scope=personal`。
- 个人查询的 `scope=personal` 会由后端根据 JWT 用户和 `family_id` 找到对应 `family_member_id`，强制过滤该成员相关流水/转账、本人账户和个人预算；前端不能传入任意 `member_id` 替代当前用户。个人报表不返回成员对比，成员对比仅属于家庭范围。
- POST/PATCH/PUT 将 `family_id` 放在请求体中；服务层校验请求体家庭与账户、分类、成员的家庭一致。资源详情和 DELETE 可仅使用资源 ID，但后端仍需从资源反查家庭并完成成员权限校验。
